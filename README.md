# OtterLife 饮食计划工作台

当前默认页面已升级为预处理和用户实时生成两个阶段，操作与验证方式参见 [WORKBENCH-V2.md](./WORKBENCH-V2.md)。下文保留旧版工作台说明。

本地验证四类餐食模板、AI 候选生成、程序搭配、离散份量求解的完整链路。启动后在浏览器操作，无需编辑器。

```sh
npm install
npm run dev
```

默认 http://127.0.0.1:4173；端口被占用会自动尝试后续端口。

## 操作

1. 修改用户基础信息、热量、营养比例、餐数、餐食形态和个性化约束，确认匹配模板。模板 JSON 可编辑。
2. 在模型设置中填写服务商、Base URL、模型名、API Key。可测试连接；每次请求会按服务商规则计费。每槽位默认10个候选，支持3–20个。提示词可修改，候选 JSON 可修改或手动粘贴。
3. 生成指定天数的候选搭配。随机种子使结果可复现，重复次数为软上限。搭配 JSON 可修改。
4. 设置热量与营养比例容差，运行求解。查看每日实际摄入、每种食物的份量、约束校验和重试记录。可导出完整实验 JSON，包含模型调用记录，不含 API Key。

没有密钥时，第二步可以载入明确标记的内置示例数据。示例数据只验证后续算法，不能当作模型效果评测。

## 模型接口

支持 DeepSeek、豆包火山方舟、通义千问百炼、硅基流动、OpenAI 和自定义 HTTPS Chat Completions 兼容接口。预设模型名需以服务商当前控制台为准。豆包需填写可用模型 ID 或推理接入点 ID。支持 JSON 模式开关和最大输出 Token。

密钥仅保存在页面内存，刷新即清除；请求通过本地 Node 服务转发给指定服务商。不输出、不导出、不持久化密钥。用户参数和求解规则存入浏览器本地存储；候选和调用记录刷新后清空，可先导出。

## 算法与验证边界

- 基础模板：中式/轻食 × 两餐/三餐。两餐另区分早餐+午餐、午餐+晚餐。所有模板均为可编辑演示配置，不代表已通过营养师审核。
- 目标演示比例：减脂25/30/45、增肌25/25/50、维持20/30/50，依次为P/F/C，均可覆盖。已有热量直接传入；估算模式使用 Mifflin-St Jeor × 活动系数 + 显式调整值。
- 每个槽位预选一种食物，再在该食物给出的离散份量中选一个。可选槽位有0份选项。求解器为 javascript-lp-solver 0.4.24，使用混合整数规划；在容差范围内尽量接近日目标热量。
- 每日热量、全天P/F/C供能比、单餐热量同时设为约束。比例以三大营养素产生的总热量为分母。每餐不单独限制P/F/C比例。
- 每天最多尝试4个组合，每组设置650毫秒求解时限；前端45秒总时限强制中止。限时未求出不等于数学上不存在可行解。未通过独立复算的结果不采纳。
- 食物份量来自模型或人工给出的档位。算法保证选自档位，档位本身是否合理仍需核实。
- 忌口与过敏首先进入提示词，随后用食材/过敏原关键词和常见别名拦截。此演示未连接真实食材关系库，不保证能发现遗漏食材、未知别名或交叉接触。
- 候选营养均为估算。热量统一按蛋白质4、碳水4、脂肪9 kcal/g计算，暂未单独处理膳食纤维、酒精等。正式产品应对接经核实的食物/标准菜谱数据库，明确生熟重与烹调油口径。
- 复合菜按成品总重量与成品每100g营养计算，尚未拆成配料清单或生成烹饪步骤。
- 模板槽位匹配和营养可行不能保证生活搭配合理；早餐适用性、食物来源可得性、口味协调主要依赖候选质量，是这次实验需要观察的指标。
- 重试会重新抽取同槽位候选，不放宽热量、比例、忌口约束；重复度可能超过软上限，输出中单独提示。
